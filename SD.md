# System Design

## Current architecture

- Short ID generated by hashing the URL with SHA-256. The bytes are encoded as text with base64: [a-zA-Z0-9-/]
- Postgres as the database. The schema is 2 columns `shortened` (PK) and `url`
- The same `url` can be registered multiple times.
- No expiration date for URL in the database.

## Improvements

- Add read replicas for Postgres
  - Write on primary, read from replicas (requires different `pgxpool` instances)
  - Trade-offs: replication errors/lag, increase cost in maintenance etc.
- Use a cache database (e.g. Redis) to off load the database.
  - When registering a new short URL, add a new entry on Redis with a TTL
  - When returning the long URL, look first on Redis. If not found, then look on Postgres and add the record on Redis.
- The database schema is pretty simple which makes NoSQL DBs a good choice.
  - There is no need for transaction
  - It does not have to JOIN multiple tables
  - _Usually_ NoSQL databases have been built with scaling functionality from the start making this process easier to achieve
- Analytics: how many times a specific URL was requested

## Notes

- `sha265.Sum256` returns `[32]byte`. To generate a string, it requires an encoding that can transform the array of bytes into a valid UTF-8 string. Go has hexadecimal and base64 encoding in the standard library, but ideally the shortened URL should be alphanumeric (upper and lower case included) only which is 62 characters.
- Postgres replication (primary/replica) has its own challenges regarding managing the instances (i.e. observability, lag, storage, configuration etc.), but in URL Shortener case the most impacting issue would be consistent reads between replicas
  - If the data replicated to instance A but not to B the user can experience inconsistent requests: the first request can succeed (read from A) but the second one returns a 404 Not Found (read from B). 
  - The problem can be solved by making the user always reading from the same instance. The assigning problem could be solved by Consistent Hashing.
